# 六智能体协作改造方案

本项目的核心是六个独立配置的智能体共同完成一个需求。Word、PPT、Excel、PDF 和代码包是协作成果的交付形式；改进这些格式之前，先让每个角色的输入、产出、交接和验收真正参与最终结果。

## 现状中需要修正的协作断点

1. `backend/main.py` 对普通单文件请求自动走直接生成，主要由一个成员写文件并调用成品评审。用户看到的是文件产出，六角色流程未实际发生。
2. `backend/graph.py` 的产品经理规划了任务，但任务分派主要依赖少量关键词；“写作/设计/其他”任务会落到前后端角色，分工与产物内容不完全匹配。
3. 开发/内容贡献可以并行生成，但交接给 QA 的主要是状态和简短摘要。QA 对代码做语法检查，然后让模型依据摘要判断测试结论；这不能证明功能测试或文档事实检查已经执行。
4. 技术主管的第一层结论主要读取任务状态；代码意见只看少量 Python 节选。非代码任务也使用“代码评审记录”。
5. 最终内容文件在 QA 和主管通过之后才由敏捷教练汇编，因而这两名角色尚未审阅最终文件。团队内容先被压成预览/摘要再交给最终生成调用，信息可能丢失。
6. `speak()` 产生的工位气泡是展示事件，不能作为任务已交接、已复核、已通过的证据。角色调用失败或兜底时，也不能把模板对话算作有效贡献。

## 六个角色的固定职责

| 角色 | 软件项目 | 文件/内容任务 | 必须留下的可检查结果 |
| --- | --- | --- | --- |
| 1 产品经理（PO） | 澄清目标、用户故事、范围和验收条件 | 识别受众、用途、事实来源、页数/篇幅及必须包含的内容 | `RequirementContract`：逐条需求、优先级、验收方法、来源或缺口 |
| 2 后端工程师（BE） | 接口、数据、业务逻辑及异常路径 | 负责数据、事实、计算口径、引用与素材忠实度 | 有来源定位的事实/数据清单或可运行实现，交给 FE 与 QA |
| 3 前端工程师（FE） | 交互、页面、可访问性和集成 | 负责读者视角的结构、叙事、版式方案与可编辑呈现 | 页面/章节设计或可运行界面，注明使用了 BE 的哪些依据 |
| 4 测试工程师（QA） | 用需求驱动测试，运行可执行测试并记录失败 | 用需求清单检查实际文件、事实、数值、页数、可读性及编辑性 | `VerificationReport`：逐项证据、失败定位、未验证原因 |
| 5 技术主管（LEAD） | 审查实现、接口整合、运行风险和 QA 证据 | 独立审阅最终文件的内容、事实、结构、视觉证据 | `ReviewDecision`：通过/打回/未验证，具体问题和责任角色 |
| 6 敏捷教练（SM） | 管理依赖、并行、返工和版本交付 | 编排各角色交接，汇总批准后的内容并生成最终成品 | `HandoffLog` 与版本记录；仅在验收闭环后宣布通过 |

角色身份不改变模型配置；继续由现有六个低价模型执行。对于简短任务，各角色的结果可以短，但不能只有气泡对话或“已完成”自述。没有适用工作的角色应明确写“本任务无需该项专业产出”，避免为了展示六人而编造内容。

## 目标流程

```text
用户需求/附件
  → PO：需求契约和验收条件
  → SM：按依赖分工，发布可引用的交接包
  → BE：事实/数据/逻辑                 FE：结构/表达/界面
             ↘ 互相核对并整合 ↙
  → 形成候选成品（真实文件或代码项目）
  → QA：针对候选成品执行检查，给出证据和定位
  → LEAD：读取候选成品、QA 证据和原始需求，独立决定
  → 不通过：只退回负责角色，修订候选成品，QA 复验，LEAD 复审
  → 通过/未验证：SM 发布版本与状态，附协作追踪和质量报告
```

**顺序原则：先生成候选成品，再由 QA 和 LEAD 检查同一个文件哈希。** 修订后哈希改变，旧结论失效，必须重新检查。只检查过程文档或任务状态不能批准最终成品。

## 交接协议（先实现这一层）

每次角色交接保存一条结构化记录，建议字段：

```json
{
  "task_id": "T1",
  "from_roster": 2,
  "to_roster": 3,
  "input_refs": ["用户需求#1", "附件A:第2页"],
  "output_refs": ["工作区中的内容/文件引用"],
  "claims": ["本次交付的可核实结论"],
  "open_questions": ["仍需确认的事实"],
  "acceptance_criteria": ["交接方要求接收方验证的条件"],
  "status": "ready|blocked|rejected|accepted"
}
```

- 记录可以放在 Sprint 工作区与数据库，前端通过现有事件流显示摘要。引用必须指向真实内容或文件，不能只保存气泡文案。
- 接收方可拒收：缺来源、缺文件、验收条件不可验证、接口不匹配时写明原因与责任角色。并行 BE/FE 的整合点必须检查共同契约。
- 保存角色编号、模型调用状态、输入来源、输出版本、文件哈希和时间。API 失败时交接状态为 `blocked/unchecked`，不使用兜底文本伪装通过。
- 模型输出和工具检查都按用户现有预算计费；暂停、停止及预算到顶时不再发起下一次角色调用。

## 两条任务路线

### 软件项目

PO 定义用户故事和可执行验收；BE/FE 按接口契约并行开发；SM 在集成前核对文件冲突和依赖；QA 对候选项目运行测试或明确未验证；LEAD 阅读实际源码、测试结果和需求；返工定位到文件/任务；最后打包同一候选版本。

### 文件/内容任务

PO 定义读者与事实边界；BE 负责素材核对、数据与公式；FE 负责大纲、叙事和版式；SM 将两者汇成候选文件；QA 打开真实文件并核对需求、数据及渲染页面；LEAD 审阅同一文件和 QA 证据。PPT/Word/Excel 的专用生成器是 FE/BE 完成任务的工具，不能替代角色协作。

现有“直接生成单文件”路径可保留为用户明确选择的快速模式；默认 Sprint 应走上述协作路线。预览页应显示路线、参与角色、预计模型调用与费用。用户明确要求单文件快速生成时，界面不得宣称六人协作已经发生。

## 代码实施顺序

1. **需求契约**：改 `backend/graph.py` 的 `kickoff` 与 `backend/agile.py`，使 PO 的每条验收条件能被后续角色引用；原始要求不因摘要截断丢失。
2. **分工与交接**：改 `assign/develop/fix`，按 `deliver_kind` 给 BE/FE 分配真实职责；新增交接记录与接收校验。现有气泡事件只负责展示。
3. **候选成品前移**：改 `deliver` 和 LangGraph 边，将候选文件/代码项目生成放在 QA 之前；保存候选文件哈希和源结构。
4. **QA 实测**：改 `test`，对候选文件调用 `artifact_quality.inspect`，对代码调用项目运行检查；逐条验收条件附证据。模型可解释结果，但不得替代实际测试。
5. **LEAD 独立复核**：改 `review`，读取同一候选版本、原始需求、交接记录和 QA 结果；区分 `passed/failed/unchecked`，不能仅凭任务状态通过。
6. **定点返工闭环**：改 `fix`，把缺陷定向发给 BE、FE 或对应文件作者；修订后重新生成哈希并走 QA→LEAD。超过上限交付“待修正”并保留证据。
7. **路线与展示**：改 `backend/main.py` 的规划/路由及前端任务、事件、产物视图，默认展示真实协作链；快速模式明确标识。用户可查看“谁基于什么做了什么、谁验证、谁驳回”。
8. **格式质量与对照**：在协作链稳定后落实总计划中的 PPT/Word/PDF/Excel/代码生成器改进，用同一批样本比较单人快速模式与六人协作模式的质量、耗时和费用。

## 协作验收标准

1. 同一个最终成品可追溯到 PO 条款、BE/FE 的真实贡献、SM 整合、QA 的实际检查和 LEAD 的独立结论。
2. QA 与 LEAD 检查的文件哈希等于最终交付文件哈希；只要候选文件改动，两个结论必须重新计算。
3. 失败问题能定位到责任角色和具体页/节/单元格/文件；未受影响的内容在返工中保持一致。
4. 断开任何一个关键角色或检查能力，系统给 `unchecked/blocked` 和原因，不能伪装六人一致通过。
5. 前端可看到实际交接与证据，同时气泡、走动继续作为协作可视化，不参与通过判定。
6. 对照测试证明协作模式在需求满足和事实忠实度上有改善；同时如实报告增加的调用、费用与时延。
