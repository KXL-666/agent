# 生成流程质量改造计划

> 目的：先把六个智能体的分工、交接、实测和返工做成真实闭环，再提高 Word、PDF、PPT、Excel 和代码项目的成品质量。本文是格式专项清单；主流程及优先顺序见 [六智能体协作改造方案](六智能体协作改造方案.md)，逐步执行说明见 [剩余13步实施交接](剩余13步实施交接.md)。完成一项就更新状态和证据。

## 首要目标：六人协作能影响最终产物

项目首先要证明六名智能体确实围绕同一需求协作，而非仅有六个模型配置和办公室动画。优先落实：PO 需求契约 → SM 分派与交接 → BE 事实/数据/逻辑、FE 结构/呈现 → 先形成候选成品 → QA 检查真实候选 → LEAD 独立复核 → 定向返工 → SM 发布。**只有六人协作链可追溯、QA 与 LEAD 审阅了最终同一版本，才进入下方各格式的深度改造。**

现有普通单文件请求可自动绕过完整协作，现有完整 Sprint 的最终文件也在 QA/LEAD 评审后才生成。这是本轮最高优先级的流程缺口；单纯替换 PPT 模板不能解决。保留明确选择的快速模式，但默认 Sprint 以协作模式为主，并如实标识实际参与的角色。

## 0. 当前基线与约束

当前入口主要是 `backend/main.py` 的直接生成、重试和修订，以及 `backend/graph.py` 的 Sprint 产物生成，最终都会进入 `backend/forge.py`。已有真实文件检查、LibreOffice/PDF 渲染、模型抽样评审、最多三轮重试和质量报告。应把这些能力接进六人交接链，不重复造平行流程。

已确认的主要缺口：

1. PPT 在 `forge.py` 中用固定的“8～12 页、每页 3～5 条要点”提示词一次生成整份 JSON；渲染器几乎所有内容页都是标题、要点、可选表格。现有两份 PPT 样本分别为 9 页和 10 页，均没有图片或图表对象。
2. Word/PDF 与 Excel 也以整份正文或整份 JSON 为主要生成单位。需求、附件依据、作者推断和待填数据没有形成可检查的中间层。
3. 评审意见虽然记录了 `location/problem/fix`，重试时仍把完整旧内容塞回提示词，重新生成整个文件。正确内容容易被改坏，长文档也可能截断。
4. 结构检查完成而模型评审不可用时，报告仍可能显示 `passed`；页面截图只抽样评审，界面需要明确区分结构检查、内容评审和视觉评审。
5. 没有固定任务集与旧版对照，无法量化质量改善，也难以发现成本和时延回退。

约束：继续使用用户已配置的六个智能体及各自低价模型；新增模型调用必须计入现有用量、预算和中断机制。不得为了提高质量静默切换到更贵模型。不得把 API Key、附件原文或敏感产物写进 Git。旧文件、旧报告、旧修订版本必须可读取。

## 2. 各步骤需要改的具体位置

### 步骤 1：固定基线

- 新建非敏感测试集和运行说明，至少覆盖：简短通知、带来源材料的分析报告、无数据的方案 PPT、有真实数值的汇报 PPT、含公式/图表的工作簿、可运行的小型代码项目。
- 将任务输入与评分维度固定；对现版产物记录六人实际贡献和交接、真实文件、质量报告、页面截图、API 用量、运行时间。后续用同一输入复跑，不把模型自评当作唯一评分。
- 为“事实忠实度、需求满足、信息密度、视觉可读、可编辑性、运行正确、成本/耗时”建立清楚的评分说明。人工盲评至少用于最终对照。

### 步骤 2：需求与依据层

- 在 `backend/forge.py` 生成前加入统一的 `ArtifactBrief`，并让 `backend/main.py`、`backend/graph.py` 的两条入口复用。字段至少包括目标格式、读者、目的、明确约束、已给事实、附件来源定位、缺失信息、允许假设。
- `backend/file_knowledge.py` 返回的片段保留文件名及页/行定位；生成内容中的关键事实能映射到这些片段或用户直接输入。引用不足时写成“建议/假设/待确认”，不要杜撰已完成工作、统计数字和外部链接。
- 保存脱敏的计划与来源索引到现有 `workspace/quality/<文件哈希>/`；质量报告记录来源覆盖率与无法核实的断言。文艺写作及明确要求虚构的任务按对应规则处理。
- 限制结构化计划的长度和模型调用次数，纳入预算；计划失败时记录 `unchecked` 并使用保守的直接生成路径。

### 步骤 3：PPT 分页规划与多版式

- 拆分 `backend/forge.py` 的 `_pptx_content_prompt`、`_gen_pptx`：先决定故事线、页数和每页的一个中心结论，再生成页内容。明确页数和封面优先于默认页数；短需求允许短演示，不强迫背景/风险/结论凑页。
- 扩展 `_sanitize_pptx` 的 JSON 协议，支持 `layout`、`claim`、`evidence`、`source_refs` 与布局所需的数据；保留旧版 `heading/bullets/table/note` 兼容。未知布局拒绝或安全降级，并在报告里说明。
- 拆分 `_build_pptx` 为可测试的原生版式组件：重点结论、双栏对比、流程/时间线、数据图、表格、简洁文本。图表只使用用户提供或可追溯计算的数值；图片只使用可信素材/明确授权的资产，不为填空白伪造示意图。
- 基于实际渲染检查每页的文本溢出、表格拥挤、字号下限、元素重叠和留白。无法自动判断的审美问题交给视觉评审并标明抽样范围。

### 步骤 4：Word/PDF 结构化写作

- `backend/forge.py` 在 `_gen_docx` 前生成目录/章节计划；复杂文档分节生成，短通知/作文等保持单次生成。保存每节源文本和合并后的 `source.md`，避免超过截断上限。
- `_build_docx` 与 `backend/pdf_builder.py` 根据内容类型选择标题层级、表格、页眉页脚、封面；PDF 优先复用 Word 源和 Office 转换，不能转换时明确记录替代构建路径。
- 按用户明确要求检查篇幅、章节与表格；逐页渲染查空页、孤立标题、表格跨页和不可读字号。不能拿固定字数阈值代替内容质量。

### 步骤 5：Excel 数据与计算分层

- `backend/forge.py` 的 `_gen_xlsx` 在生成公式前明确输入列、类型、单位、来源和计算口径；`backend/spreadsheet_builder.py` 保留原生公式、验证、图表与来源批注。
- 解析公式依赖，检查引用单元格/工作表、循环引用、外部引用、错误值和 LibreOffice 重算缓存。图表范围排除合计行并对应真实数值。
- 比对附件记录数和工作簿明细数；缺输入时生成可填写模板，不捏造业务值，也不把空模板误判为已完成数据分析。

### 步骤 6：代码项目契约与运行验收

- 在 `backend/project_agent.py` / `backend/graph.py` 生成项目计划时保留每个功能的输入、输出、错误路径、验收测试及所属文件。
- 静态检查之外，使用已有隔离运行器安装依赖、构建、执行有实际断言的测试；Docker 不可用保持 `unchecked`。修复失败只修改相关文件和测试，不以删测试冒充通过。
- 成品说明里区分已运行、仅静态通过和未验证，附可复现命令与错误摘要。

### 步骤 7：定点修订与版本选择

- `backend/artifact_quality.py` 规范评审问题为 `location/problem/fix/severity/evidence`，不要只传一段字符串。结构检查失败也定位到具体页/节/单元格。
- `backend/forge.py` 根据格式执行局部修改：PPT 替换单页 JSON，Word/PDF 替换单节 Markdown，Excel 修改指定表/单元格，代码只改相关文件。若定位不可靠，显式回退整份修订并记录原因。
- 每轮保留源结构和差异；未受影响部分做一致性校验。候选选择先满足用户硬约束和无事实错误，再比可读性、内容评分，分数相同时选择修改较少且成本较低者。
- 手动 `/api/artifacts/{id}/revise` 使用同一修订机制；旧版本可下载、可比较。

### 步骤 8：质量门禁与证据

- `backend/artifact_quality.py` 的总状态由必需维度汇总。`review=unavailable/not_run` 时内容评审为 `unchecked`，不能仅因文件可打开就给总状态 `passed`。视觉输入被模型丢弃时视觉维度也必须是 `unchecked`。
- 事实检查包括来源覆盖与高风险断言；结构检查包括文件可读、页数/字数/行数等明确约束；运行检查只适用于代码和公式。检查粒度与证据范围写入报告 schema，旧 schema 能兼容读取。
- `backend/main.py` 与 `backend/artifacts.py` 使用最终报告状态；`failed` 明示待修正，`unchecked` 明示未验证。下载不丢失，正式“验收通过”标签只授予真实通过的产物。

### 步骤 9：前端反馈与手动修订

- `src/components/ArtifactQualityPanel.tsx` 分开展示结构、事实、内容、视觉、运行结果；截图抽样页码、未验证原因、问题定位、各轮变更都可见。
- 生成进度显示“分析需求→规划→写作/制图→渲染→检查→局部修订”，并呈现额外模型调用与费用。前端用现有事件和用量系统，避免单独维护一套状态。
- 手动修订说明支持“第 4 页图表”“预算表 C12 公式”这样的定位；无定位时照常支持自然语言修改。

### 步骤 10：对照评估与收尾

- 用步骤 1 固定集复跑，记录每项通过、失败和未验证，避免只展示成功案例。对照至少检查生成文件的真实页面、原生对象、来源忠实度和可执行结果。
- 后端针对 schema 兼容、来源缺失、页数、图表真实性、局部修订不改其他页、评审不可用、预算中断写有意义的回归测试；前端跑 `npm test`、`npm run lint`、`npm run build`。
- 更新 `README.md` 和 `docs/多格式产物质量引擎.md`，只写实际具备并验证过的能力。记录改造前后质量、成本和耗时；改善不明显的模块继续调整，直到达到验收标准。

## 3. 统一验收标准

1. **需求**：明确的篇幅、格式、受众、必须内容和禁忌内容全部满足；缺素材不能被编造成既成事实。
2. **事实**：业务数字、结论和引用能回到用户输入/附件位置或明确计算；模型推断、示例、建议与事实分开。
3. **文件**：实际文件能打开、可编辑；Word 标题/表格、PPT 图形/图表、Excel 公式/图表等使用原生对象；PDF 文字可搜索。
4. **视觉**：所有页完成渲染和机械边界检查，必要的视觉评审报告样本范围；明显溢出、空白页、拥挤和难读文字不能标通过。
5. **修订**：指出一个位置的问题后，只改相关位置；正确内容不回退；三轮仍失败则保留最佳候选并标待修正。
6. **状态**：检查失败为 `failed`，必需检查未做为 `unchecked`，所有必需条件完成且通过才是 `passed`。界面不把“自动检查通过”写成“人工验收通过”。
7. **成本**：继续使用现有低价模型配置，记录新增调用、tokens、耗时与费用；预算/停止动作能中断新流程，不因优化质量失去成本控制。
