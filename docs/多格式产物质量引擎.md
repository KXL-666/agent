# 多格式产物质量引擎

本轮将 Word、Excel、PDF、PPT 和代码项目接入专用构建器、实际文件验收和有限修订流程。目标是提高可交付质量，不能仅凭本轮改动就宣称与所有商业 Agent 达到相同水平。

## 从实际成品获取反馈

流程为：理解需求与素材 → 专用制作 → 检查真实文件 → 渲染与内容评审 → 基于上一版定点修订 → 保留较好版本 → 发布到交付目录。

默认最多制作三轮。校验失败或模型评审提出具体问题后，下一轮获得问题和上一版完整正文或 JSON 结构，避免只凭几句意见整篇重写。渲染失败保留上一版文件。并发请求的文件、来源、报告与项目记录保持独立。

Word/PDF 源 Markdown、表格/PPT 源 JSON、页面图片和验收报告保存在 `workspace/quality/文件哈希/`。最终目录仍只保存交付文件。编辑 Word/PDF 优先读取完整源正文，不把预览摘要当作全文。

## 各类型能力

| 类型 | 实际制作能力 | 实际检查范围 |
| --- | --- | --- |
| Word | 原生标题与导航、原生编号、按内容分页的表格、重复表头、按需封面 | 文件可读、标题、内容重复、明确篇幅要求、实际页面边界、内容与截图评审 |
| Excel | 原生公式、图表、批注、格式、条件格式、下拉验证、打印区域 | 原生公式与图表是否存在、真实重算结果、错误值、实际打印页面、内容与截图评审 |
| PDF | 优先从 Word 同源导出；独立 ReportLab 作为无 Office 环境的构建方式 | 中文可搜索文本、书签、真实分页、字符与页面边界、内容与截图评审 |
| PPT | 原生内容页、表格和备注，尊重明确页数与封面要求 | 元素边界、实际页面、明确页数要求、内容与截图评审 |
| 代码 | 项目规划、角色贡献整合、完整文件、入口、依赖、README、测试及错误修复 | 计划文件、语法、未实现标记、测试断言；可用沙箱中安装依赖、构建和执行测试 |

不再用统一的 1,500 字、8 行等下限衡量所有文件。篇幅依用户要求检查，无法确定的范围交给内容评审，不通过凑数提高质量。

## 执行与验收边界

Office 内容构建不执行模型生成的任意脚本。代码生成保留源文件；主机只做静态解析与语法检查，依赖安装、构建和功能测试交给独立 Docker 容器。

依赖安装阶段不挂载用户目录、API Key 或 Docker socket，源码只读挂载；测试阶段禁止网络，以非 root 用户运行，并限制 CPU、内存、进程数和运行时间。仅进程退出码为零仍不够，还要求非零测试执行证据。检查失败后可修复，修复不能通过删掉功能和测试来冒充通过。

当前默认执行器支持 Python、Node；其他语言可以生成完整源码，但没有对应工具链时明确显示未验证。Web 项目若需浏览器测试，还需选择带浏览器依赖的执行镜像并提供相应测试。

本机已准备 LibreOffice、ReportLab 和 PyMuPDF。Docker 服务当前不可用，因此隔离容器中的依赖安装/构建仍为未验证。固定集的 C1 新流程因贡献冲突未形成代码包；离线集成测试另用可控 BE/FE 文件实际运行温度换算、README 和断言测试，但这不等于模型协作生成的 C1 通过。

截图评审最多抽样六页，不能替代逐页人工验收；所有页面单独进行渲染与基础边界检查。模型不可用、模型不支持视觉、缺少渲染器、缺少执行沙箱等情况与实际失败分别记录。

## 实测记录

使用当前配置的模型与固定样例输入，实际测试了：

- Word 项目周报：约 200 字要求，最终正文统计 196 字。实测发现并修复标题层级和双重编号问题；定点修订后内容和页面截图评审通过。
- Excel 预算对比：三个项目的预算与实际输入，6 个原生公式和 1 个原生柱状图；真实重算、内容与页面评审通过。分类图表默认排除合计行，避免与明细重复比较。
- PDF 验收说明：实测发现中文行首标点问题后，改用同源 Office 排版导出；可搜索文本、分页、内容和截图复验通过。
- Python 温度换算项目：真实模型生成入口、包结构、README、标准库依赖说明及测试文件；计划文件、语法、未实现标记与断言检查通过，运行验证因无沙箱保留为未验证。

这些是固定输入的小规模功能与质量样例，不是与外部商业 Agent 的盲测。大文档、复杂公式、复杂应用、素材忠实度和主观视觉质量仍需扩大任务集并持续评估；代码是否真正满足需求必须以运行测试与实际使用验证。

已将上述四类真实模型产物保存到独立历史记录「【多格式质量实测】Word、Excel、PDF、代码（固定样例输入）」，可在产物中心下载并查看验收详情。原有项目迭代仍在历史记录中。

固定集的协作复跑已经完成记录，但协作样本没有一个形成完整通过交付：W1 有候选且 QA 通过，LEAD 因内容/版式问题判失败；D1 的 QA 未完成且 LEAD 哈希与当前候选不一致；P1/P2/X1 因贡献缺失阻断成品生成；C1 因 BE/FE 文件路径冲突阻断合并。W1 快速模式另有自动质量检查通过的单页文件，不代表六角色协作能力。详情见 [改造后 W1 复跑记录](改造后W1复跑记录.md) 和 [六样本记录](生成质量基线样本.md)。

生成调用遇到服务商故障时，部分文本/文件路径现在可使用现有低价 DeepSeek roster 1/2 配置接管，同时保留当前角色的系统提示并按实际调用模型记录用量。接管只解决调用可用性，不代表贡献内容或最终成品通过验收；PPT/Excel 路径已由离线测试覆盖，未做新的在线样本验证。

## 单文件请求的快速路径

当用户明确要求生成一个 Word、PPT、Excel 或 PDF 文件，且没有要求软件开发或团队协作时，Sprint 会直接进入文件生成、真实格式检查和成品评审，不再为单文件任务创建模拟开发、测试和返工轮次。Sprint 历史、成本统计、暂停/停止和预算限制仍然生效。软件项目或明确要求团队分工、任务拆解的需求继续使用完整敏捷流程。

## 部署与回归

Windows 可使用 `scripts/setup-artifact-runtime.ps1` 下载并校验官方 LibreOffice 包，解包到项目工作目录并安装 Python 依赖。也可预装 LibreOffice 或通过 `OFFICE_SOFFICE` 配置。工具目录与质量缓存不进入 Git，备份排除工具安装目录。

代码运行验收需另行准备可用 Docker 服务。可通过 `OFFICE_PYTHON_IMAGE` 和 `OFFICE_NODE_IMAGE` 配置测试镜像；镜像应包含任务需要的可信工具链。

后端回归命令：

```powershell
cd backend
python -m unittest test_core test_graph test_improvements test_artifact_engine -q
```

前端执行 `npm test`、`npm run lint`、`npm run build`。回归覆盖真实 Office/PDF 构建、公式重算、不可用工具状态、定点修订、原生编号、文件路径校验、隔离运行命令约束以及验收 API。
